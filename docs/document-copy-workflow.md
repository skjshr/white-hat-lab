# 日報と編集コピーの作業面

## 現在のプレイから選んだ問題

前サイクルで実際に入金したDAY6の会社から、通常の「社員が日報を保存できない」を受注した。改修前の通常GUIでは、960×600・文字130%のファイル一覧とプレビューが縦の大きな枠に分かれ、日報の内容が画面の下へ押し出されていた。前日分を取得してエディターを開き、変更せずに送ると実際に保存を拒否された。この経路では、取得した資料と編集するコピーの関係が配置から分かりにくかった。

今回の達成条件は、日報全体と編集・送信を同じ作業面で扱えること、未保存の編集と取得時の内容を区別できること、エディターから戻ると実際のコピー状態が更新されること。許可の拒否、セーブ失敗、再試行、再開を挟んでも実データを保持し、最後の読み戻しと納品・入金まで確認する。

## 画面と実データ

エクスプローラーの一覧は小さなファイル対象にし、選択した実際の内容を角を折った紙の上に表示する。右側のコピー、編集、共有へ送信を矢印でつなぐ。コピーなし、未保存の編集、保存したコピー、取得時と同じ内容を、形・記号と短い状態名で区別する。パスと接続先は閉じた詳細に移した。日報を構造化したサンプルや合計値へ置き換えず、任意の取得ファイルの実際の文字列を保持する。

取得時の紙は保存した応答の内容。コピーの編集や別ソフトへの移動では、紙を現在の共有先の内容にすり替えない。実際のGETによる読み戻しで初めて紙が更新される。コピーは模擬VMの `/home/operator/report.txt` に置かれ、別の物理端末を新設した表示にはしていない。

エディターからファイル画面へ戻る操作は、下書きと保存されたコピーを読み直して表示するだけ。ネットワーク要求・測定・仕事時間の加算を行わない。取得後には編集操作へキーボードフォーカスを渡し、Tab・Enterで続けられる。フォーカスの一時フラグはセーブへ書き込まない。用紙の高さは実際のフォント寸法に合わせ、長いファイルの内容には既存のスクロールを残す。

転送の保存に失敗すると実データを戻し、入力と失敗を残す。同じ入力で再試行して保存できると、下部の失敗表示も短い「転送保存済み」に更新する。受注票の長いホバーヒントも短い名称へ替え、詳細は対象を選んで開く。

既存のソフトの用途は維持する。ファイルを選んで扱う構成は [Windowsのエクスプローラー](https://support.microsoft.com/en-gb/windows/experience/fileexplorer/file-explorer-in-windows) を参考にし、共有管理の接続図や設定を扱うCockpit、コードと下書きを扱うエディターとは別の画面にしている。

## 通しプレイの証拠

記録はローカル `../audit/daily-workspace-20261006/`。通常GUIの改修前の取得・編集・保存拒否を3枚の画像に残した。通しの検証は既存の市場に出現している案件を、実際の前サイクルの完了セーブから受注するGodotネイティブ入力。資金・技能・市場・正解設定・測定結果は注入していない。背景の作業時計は停止するが、明示的な仕事時間と経費は加算する。

ファイル取得、実キーによる複数行の編集、未保存コピーの送信拒否、コピーの保存、実際のACLによる転送拒否、入力を残したセーブ再開を通す。来客を通す誤対応は社員の保存を復旧しても納品できない。来客を拒否した後、転送保存の失敗・ロールバック・同じ操作の再試行、実際のGETで本日分を読み戻し、再検証・納品・請求入金・結果の保存再開まで進める。

最終記録 `native-narrow-final3` は実描画960×600・文字130%、`native-wide-final3` は通常の1920×1080設定・文字100%（Windowsでの実描画1908×990、論理領域1387×720）。それぞれ433確認・66クリック・108キー・不合格0。スクロールは小画面22回、通常サイズ2回。Godotは終了を待って順に実行した。これは自動入力の経路数であり、初見の人が必要とする操作数ではない。全ての紙・コピー・主要操作の矩形と日報5行の表示領域を検査し、前後の画像も目視した。

この繰り返しの経路では仕事時間が116分になり、90分の期限を超過する。基本料は合意した¥3,240から¥3,053へ減額、加算¥0、経費¥700、純利益¥2,353。現金は¥55,964から¥58,317、つばさ文具の満足度は75から60、請求書 `INV/0008` は入金済みになる。期限や時計を上書きして成功扱いにしていない。履歴、結果票、顧客満足度、入金後の現金をセーブ再開して比較する。

既存の日報の時間内納品も960×600・130%の実入力で320確認・50クリック・64キー・不合格0。従来のファイル操作は56確認、SambaのUI確認は不合格0。実装前に通常GUIで受注した案件のセーブ互換は15確認、実プレイヤーの旧セーブは33確認で不合格0。後者の2系統はバックエンドの読み込み・保存・再開の確認で、初見プレイではない。受注済みの元のファイル・検証対象を維持し、新しい保存形式への変更はしていない。

元プレイヤーのSHA-256は `9ceabc887485dc835df3dec6e89b75c96a600025b54b4090d5b422e062c110f8`、前サイクルの完了セーブは `31680c91269cc3eec26a692c6af9b2794ee2596ccca14d12b97cd603315bb77b`、実装前に受注したセーブは `3e0d29d2c42d09e3a4b5459b98ba8ae209bff5a6ad14dcf4faad6e7cc4997800` を保持した。エディターの全スクリプト読み込みも成功し、最終ログにスクリプトエラーはない。

改修後も通常GUIで保存拒否後のQAセーブを再開した。ファイル選択後のEnterで編集へ進み、前日分の9件を12件へ実キーで変更。ファイル画面へ戻ると紙は9件の取得内容を保持し、コピーに鉛筆と「未保存の編集」が現れた。未保存の送信を拒否し、保存した後も共有のACLで実際に転送を拒否した。紙と保存したコピーの表示を `04-after-paper-and-copy.jpg` から `07-after-saved-copy-and-denial.jpg` に記録した。通常GUIのこの確認は納品まで通しておらず、通しの納品・入金は前述の自動入力による証拠。

検証中に、取得後のフォーカス消失、別ソフトから戻ったコピー表示の更新漏れ、通常文字サイズでの用紙不足、転送再試行後の古い保存失敗通知を見つけて修正した。入力テストの改行はUnicode値だけではCodeEditに改行されなかったため、実際のEnterキーへ修正した。描画処理のRect2 API誤用もコンパイル検査で修正した。失敗ログは削除していない。

## 限界と次の課題

初見の第三者プレイヤーは未検証。自動入力の成功を、理解のしやすさや楽しさの証明とはしていない。通常起動直後の外部取得画像が暗くなる現象は、[内部描画と外部取得の切り分け](startup-observation.md)を参照する。今回その原因が解消したとは扱わない。

通常GUIの保存後、通知が消える間にタスクバーのアイコン位置が変わり、ファイルへ戻るつもりでメールを開いてしまった。次サイクルでは、ソフト間を往復する主要操作の配置を安定させることを最優先にする。

その後の課題は、コピーから共有への書き込みと拒否の位置が画面だけで分かる転送画面。現在のアップロード画面はパス入力と文字の結果が中心で、今回の紙とコピーの作業面とのつながりが弱い。また、丁寧な確認が期限超過になる仕事で、必要な調査と不要な再測定を判断できる表示は引き続き検証が必要。
