# 納品の成果を精算の紙面で確認する

開始時点は `e167cc9`。最新の作業ブランチを確認してから、通常GUIで実際に完了したDAY5「支店の業務再開」を再開した。従来の「顧客の結果」は三台の検査ログで埋まり、評価・顧客満足・信用・会社レベルを読むには複数回スクロールする必要があった。元画像はローカル `../audit/receipt-outcome-20261006/01-customer-before.png` と `02-impact-before.png`。

達成条件は、最初の表示で納品評価、期限、顧客満足の前後、会社の信用・レベルの前後、売上・経費・案件利益を確認できること。各対象の紙を選ぶと、その対象の保存済み実測を開けること。色以外でも増減・期限超過・赤字・不明を判断できること。描画・記録の閲覧・再開で報酬、顧客関係、次の相談、測定を変えないこと。960×600・文字設定130%でも主要な数値と操作を検証する。

## 紙面と記録の区別

納品・精算はクリーム色の紙面、留め具、二重の評価印で構成する。顧客満足は0〜100の目盛りに変更前の線と変更後の矢印を重ね、信用とレベルは前後の数値と符号付き増減で示す。売上から経費を差し引く横長の計算式と比率の帯を置き、赤字は負号と斜線でも表す。文字中心の一覧を追加する方法を避け、ERPのラック・CSV・帳票、監視の設備配置、診断の実測台と別の構成にした。

描くのは `last_receipt` の保存済み評価であり、現在のVMから再判定しない。対象の✓・×と件数は保存した**納品判定**を数え、全部が実測であるとは表示しない。対象を選ぶとその対象だけの保存済み応答を開く。全対象の判定・初回との比較は別の明示操作でも開ける。実測がない旧対象は、他対象の応答を借りず「保存されていない」と表示する。旧精算の欠けた評価・前後値・対象名・ホスト・応答は作らない。

金額は案件利益であり、入金額や現金増減とは区別する。機材が別途請求対象のときだけ売上へ含め、利益は保存された `net` を使う。請求書の現在の状態は実際の請求台帳から読み、確定待ち、請求済み、入金済み、請求なし、不明を示す。[Stripeの請求状態](https://docs.stripe.com/invoicing/overview)のように、発行前・請求後・支払い後を分ける考え方を参照した。実サービスへの通信・課金は行わない。

## 検証方法

`test_receipt_outcome_native.gd` は `test_business_source_native.gd` の、通常資金で自然に出た三台の支店案件を使う。受注準備だけ公開APIで行い、修復、保存失敗と再試行、不正な注文の提出、原本復元、再取得、三台の実診断、納品、請求確定、入金はGodotのマウス・キー入力で操作する。背景時計だけを止め、操作費用は残す。結果の第一画面、文字幅、設定倍率、各対象から正しい応答を開くこと、Enterで選んだ紙へ戻ること、保存後の再開で資金・履歴・顧客関係・次の相談が不変であることを調べる。

`--late` は修復済みの仕事を通常の日次締め操作で翌日に持ち越し、期限超過の納品と顧客満足の低下を検証する。3Dオフィスを省いたInterfaceの環境なので、管理画面への入口だけUI APIで開く。日次締め・精算・翌日の案件再開は実際のボタン操作で、時間・評価・資金・回答を代入する方法は使わない。

関連の `test_company_billing_ui.gd --receipt` は合成精算を使う部品回帰。赤字、機材請求、旧精算の不明値、実測あり・なしが混在する対象の証拠範囲、描画が取引を起こさないことを検査する。`test_journey_outcomes.gd` は修復準備にVM APIを使う回帰で、通常資金の通しプレイとは分けて扱う。

通常GUIの手動操作、自動入力の通し検証、合成精算の部品検証は別の証拠である。初見プレイヤーの理解や面白さの検証は未実施。

検証中に見つけて直した点は、評価印と期限表示の重なり、証拠から戻る際と測定変更後のフォーカス消失、実測がない対象に他対象の応答を表示する可能性、未使用の証拠選択欄の解放漏れ、実作業時間と納品までの経過の混同。実測なしの選択欄の解放後、請求UIテストの終了時リソース警告も解消した。
