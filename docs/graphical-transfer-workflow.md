# コピーと共有を結ぶ転送面

## 今回の問題と達成条件

最新の `d1c013e` を取得して通常GUIを再開し、保存済みコピーを「共有へ送信」した。画面はローカルパスとリモート名のフォームに変わり、実際の拒否後もほぼ同じままだった。送る物、相手側の内容、拒否された位置が途切れることを今回の優先課題とした。

達成条件は、保存したコピーと取得時の共有を並べて見比べられ、実際の送信・拒否・保存の取り消しを接続と形で区別できること。同名の別ファイル、別の送信先、変更後の設定に、前の応答を流用しない。再開後も入力と実際の応答を保ち、受注から納品・入金まで通す。960×600・文字130%と広い画面で主要な物と操作を確認する。

## 作業面と実データ

[WinSCPの二面配置](https://winscp.net/eng/docs/ui_commander)を参考に、左に編集コピー、右に共有フォルダーを置いた。コピーは実際の保存内容、共有はその利用者・共有・ファイルについてGETで取得できた内容だけを表示する。未取得の相手を、VM内部の内容で埋めない。「コピー」「顧客資料」の区別をファイル選択に加え、パスと生の応答は詳細へ移した。

保存済みコピーの見出しをつかんで共有へドロップすると、送信ボタンと同じ実際のPUTを1回実行する。フォルダーは受け渡せる位置で枠が変わる。エディターの未保存内容は送れない。送信ボタンはTab・Enterでも操作できる。閲覧用の紙はTabを入力文字として取り込まず、次の操作へ進める。本文の選択と長い文書のスクロールは残す。

応答のない経路は点線と「○ 未転送」、実際の権限拒否は接続線上の×と「共有で拒否」。実際の保存失敗は「転送を取り消し」と共有側の紙の上の×を表示する。成功後は対象名、実際の要求番号、保存済みバイト数の受領表示へ戻る。バイト数は文字数ではなく、実際に送った内容のUTF-8の長さである。

要求の記録は明示的なGET／PUTの呼び出しで作り、向き・利用者・共有・元のパス・相手の名前・応答・成功時のバイト数・内容の指紋・実行時の接続と適用設定を保持する。図の描画、入力の変更、詳細表示、ソフトの切り替えでは要求を作らない。条件が違う図は「未転送」となり、前の応答は詳細に残る。これはクライアントが受け取った記録であり、権限や納品成功を推測する仕組みではない。

一覧への復帰でも応答文字列だけで転送結果を選ばない。社員のPUTと来客のLSが同じ `NT_STATUS_ACCESS_DENIED` を返す実例で、過去の転送受領表示を別の操作が借りる問題を見つけた。現在の操作・利用者・共有が一致する場合だけ受領表示を出し、来客の一覧は一覧自身の拒否を表示する。再開しても、私的な取得内容と現在の一覧結果を混ぜない。

セーブのバージョンは変えず、既存の作業セッションに記録を保存する。古いセッションに記録がなければ未測定として扱う。既存の顧客ファイル、検証条件、受注・報酬の規則は変更していない。

## 検証の範囲

経営の通し経路は、前に実際に納品・入金したDAY6の会社をQAへコピーし、自然に出現している日報案件を受注している。見積拒否・下書き再開・受注保存失敗と再試行、日報取得、実キーでの編集、未保存の送信拒否、実際の権限拒否と保存再開、来客を通す誤対応と納品拒否、設定の修正、転送保存のロールバックと再試行、読み戻し、納品・入金・結果の再開を確認する。資金・技能・市場・正解設定・結果は注入しない。

描画と入力の変更がVM・要求記録・作業時間を変えないこと、同名の違う元ファイルと未取得の送信先が前の応答や共有内容を借りないことも、この経路で確認する。原本は書き換えず、背景の時計を停止して明示的な作業時間と経費は残す。繰り返した対応は116分／期限90分となり、遅延の減額と信頼低下を保持する。

ドラッグの自動イベントだけの確認では、Godotの入力位置とWindows側のカーソル位置が食い違い、ドロップが成立しなかった。合格扱いにはしていない。`--external-drag` では実際のウィンドウでskyを用いてカーソルを開始位置へ合わせ、紙から共有の本文へドラッグする。Godotがドロップ成功を記録し、要求番号が1だけ増えたことを確認してから、同じ通し経路を続ける。これは既知の操作を行う開発者の検証であり、初見プレイヤーではない。

画像検査で、保存失敗の印が紙の裏に隠れていたため、別の子部品として紙の上へ置き直した。実キーの確認で、閲覧用のTextEditがTabを取り込んでいたため、[GodotのTab入力設定](https://docs.godotengine.org/en/stable/classes/class_textedit.html#class-textedit-property-tab-input-mode)を変更し、取得した紙と二面の紙から実操作へ進めることを確認する。

## 限界と次の確認

操作と保存の成立、図の情報源、主要部分の表示を確認する。初見の第三者による理解・楽しさは未検証。[起動時の外部取得画像](startup-observation.md)の暗転についても、描画と外部取得を区別し、原因の限界を維持する。

通常GUIで案件のOutwatchメールも開いた。送信元と締めの滞留の事情は読めるが、本文とターミナル・納品への移動が中心だった。次のサイクルは、改修後の受注から結果を再度プレイし、顧客から届く連絡で「何が直ったか」「仕事が止まっているか」を操作結果から確認できるかを優先して調べる。転送面だけの成立を、全ソフトの改善完了とは扱わない。
