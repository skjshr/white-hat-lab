# 台帳の復元を直接操作する作業台

00446a2の画面も文字への依存が強かった。保存版の一覧と選択欄が重複し、復元入口が分散していた。書類は数値表の輪郭で、選択・操作・結果の関係は周囲のラベルから読み取る必要があった。今回の対象は代表の破損台帳案件 `service-1-case-3` の復元作業面である。

## 配置の選択

「保存版の紙と復元先を並べる作業台」と「保存版の列から検査台、復元先へ送る横送り配置」を比較した。作業台を選ぶ。選択している紙と実際に変わる復元先を同じ場所で追え、狭幅で検査台を別画面に分けずに済むためである。初見ユーザーによるA/B試験ではなく、設計と実装の比較である。

## 表示と操作の約束

保存版の紙そのものを選択し、復元先で実際の変更計画を作成・確認して実行する。表示は保存内容、実ファイル、既存の顧客照合と保全記録を使う。紙の見た目が正常でも顧客合格を先取りしない。壊れた最新版をコピーすれば復元先の紙も壊れたままである。

復元先と稼働中の原本は別の場所に置く。原本と対象外の保持は、その保管物に付く印で示す。変更前の安全な状態と、これから原本を上書きする計画は混同しない。保全基準が不明なら成功の印を出さない。

短い名称、実データ、行先、実行前の必要な警告を残し、パス・ハッシュ・コマンド結果は必要時に開く。既存の計画fingerprint、権限、保存失敗時の巻き戻し、案件の合否・費用を維持する。別の案件やファイル管理の機能は既存Backrestから利用できる。

## 検証記録

書類の表示矩形をアプリ領域に対して測ると、選択した保存版と復元先の2枚は6.10%→11.46%。比較できる未選択版も含む3枚では17.19%。狭幅では選択2枚の面積は15.37%→15.45%とほぼ同じだが、版選択・復元・結果・保全を同じガイド非表示画面に収めた。背景の余白を物体の面積に数えず、重なる領域は二重計上しない。

最終ソースのnative検証は1920×1080・100%と960×600・Game/Interfaceとも130%で、各309 assertions、失敗0、exit 0。各25クリック・25キー、主要4操作を実Tab/Spaceで確認した。狭幅の15wheelには比較用にガイドを再表示した後の細かいwheel2回を含み、主操作の必要回数とは分ける。新しい初見ユーザーテストではない。

1. **対象・保存版の選択：確認済み。** ファイルを明示選択し、未確認の紙は開いて実読取結果を確認。候補の変更で古い確定操作は無効になる。
2. **破損版の復元：確認済み。** 実計画と確定を経ても、コピー先が壊れていれば照合は不一致のまま。
3. **旧版の復元と保全：確認済み。** 同じトレーで実変更計画を確認し、保存失敗の巻き戻しを経て再実行。実際の台帳値と原本・対象外保持を表示する。
4. **再読込・検証・納品：確認済み。** 状態保存後の再開と実診断、納品まで到達。説明・raw詳細は主経路で開かない。

独立した関連6テストも合格。新規workbench境界100、backup authorization91、integration53、visual semantics154、既存backup console、service workflows98を含む。表示先、対象外のファイル、未確認・古いキャッシュ、旧保存の全件復元計画、従来フォームでの復元後の継続を検査した。従来フォームの継続で見つかった自動クローズの範囲を修正し、最終ソースで再検証した。製品・対象テストのハッシュは最終回帰の前後で一致する。

原本保全の表示は現在の状態であり、書き込み予定の安全性とは別である。危険な行先への変更は実行前に警告し、設定変更後は計画の再確認を要求する。狭幅の確認画面や詳細ではスクロールが必要な場合がある。ブラウザ末尾から順TabでOS側へ移る既存の境界も残り、再確認後の確定へは実Shift+Tabで戻る。描画面積と文字数は補助指標であり、それだけで直感性や楽しさを保証しない。
