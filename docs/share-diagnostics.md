# 共有診断と手元の原本照合

開始時点は `19a0dd7`。通常GUIで進行中のDAY5案件をQAコピーから再開し、手元の注文原本が合格していても社員の共有一覧取得は `NT_STATUS_BAD_NETWORK_NAME` になる状態を実際に操作した。従来は双方を説明文と長いSHA値で表示していた。

今回の達成条件は、共有先の不在・認証失敗・操作拒否・成功を異なる位置と記号で見分け、一覧取得と内容の一致を混同せず、修正後の再測定と保存再開まで追えること。HTTPの暗い通信作業台と区別し、共有は薄紫の利用者・フォルダー・紙のアクセス図、原本は左右の紙を比較する作業台にした。文字は名称・短い状態・数値に使い、要求、受入条件、停止した段階、全64桁、初回/最新の応答は図を選んで開く。

操作構成の参考は[WinSCPの左右に手元と接続先を置く画面](https://winscp.net/eng/docs/ui_commander)。ゲーム内では利用者、共有、取得できた資料の関係に合わせて構成を変え、HTTP・共有・原本の検査を同じ一覧の名前違いにしない。外部へのファイル送信や実ネットワーク接続は行わない。

## 保存した証拠から分かる範囲

`share_diagnostic_observation.gd` は公開コマンドと保存済みの応答だけを投影する。Game/VMを読まず、設定から測定値を推測しない。受入合否は既存の判定を維持する。共有先がなくても拒否条件に合格する従来の判定は、実際の「共有先なし ×」と別の受入印で表示する。

| 観測 | 表示できること | 表示しない推測 |
| --- | --- | --- |
| LS | 応答にあるファイル名と件数 | ファイル内容・原本一致 |
| PUT/GET成功 | 実応答の対象名と転送方向 | 内容・バイト数・SHA値 |
| BAD_NETWORK_NAME | 共有先で停止 | 権限による安全な拒否 |
| LOGON_FAILURE | 利用者の認証で停止 | 有効な利用者への接続 |
| ACCESS_DENIED | 要求した操作の拒否 | 特定のACLやGET保存先が原因という断定 |
| SHA-256 | 要求した手元のパスの64桁比較 | SMB経由でアクセスできたという判断 |

未計測は疑問符、古い結果は「以前の/以前は」と変更前の印・破線・黄褐色で示す。成功の古い記録を現在の緑の合格経路として表示しない。再生は保存済み記録の約1.4秒の描画で、自動計測や架空の常時通信を作らない。

旧応答は型のない文字列のため、今回の一覧投影は拡張子のあるファイル名と `0 files` を識別する。日本語の名前も保持する。型が不明な文章、JSONエラー、使い方、未知の応答は一覧成功にせず、生の応答を残す。拡張子なし・先頭がドットの名前などの一覧は現時点で未特定となる。SHA応答のパスが要求した絶対パスと一致しない場合も照合値を確定しない。これらは表示上の保守的な制限で、VMの実行結果と納品判定を変更しない。

## 検証と残る課題

記録は `../audit/smb-diagnostics-20261005/`。通常GUIの開始前画像は `01-before-local-original-text.png`、`02-before-share-unavailable-text.png`。プレイヤー本体のセーブを使わず、QA保存先で実操作する。

通し検証 `test_share_diagnostic_native.gd` は公開のキャリア操作でDAY5の案件を受注し、Godotのマウス・キー入力で設定、業務データ変更、復旧、診断、納品、請求、入金を進める。設定から観測を作らず、保全原本が一致していてもSMB共有が不在の状態、正常な業務データ変更で原本照合だけが失敗する状態、来客の操作拒否を比較した。SMB書き込み後のセーブ失敗では、共有の実データ・時刻・資金・保存済み観測が戻り、再試行で正しいファイルを保存できることも確認した。途中のUI破棄とセーブ読込から、共有先不在と原本のバイト列が復元される。

| 通し検証 | 結果 | 入力の記録 |
| --- | --- | --- |
| 1920×1080・文字100% | 3977チェック、失敗0 | 441クリック・580キー・21スクロール |
| 960×600・文字130% | 3992チェック、失敗0 | 444クリック・580キー・29スクロール |

両方で受入評価A、`INV/0005`の入金11880、経費700、純益11180を確認した。資金30014→41194、信用250→361、顧客満足70→75、会社レベル6→7になり、案件成果が経営の保存状態に残る。これは既存の経営処理に新しい診断画面をつないだ確認で、今回報酬の判定を作り替えたものではない。通し検証後の名称・ファイル図形の間隔・ホバー文字色の仕上げは、広幅と狭幅の `test_diagnostics_ui.gd` と通常GUIで追加確認した。

Windowsからの手動プレイでは1280×720の通常GUIで、共有設定を保存しただけでは「共有先なし」が続くこと、適用・再起動で一覧3件を取得できること、その後も社員の書き込みは拒否されることを確認した。社員の書き込み許可を反映して再試行すると実際に `orders.csv` が増え、一覧は4件になった。通常終了後に起動し直して4件の結果を再開し、原本も実測し直して一致した。手動操作の範囲は共有元の復旧と原本確認で、案件全体の納品・入金は上記のGodot入力による通し検証の証拠である。

再開画面は `09-manual-resumed-share-graphical.png`、原本比較は `11-manual-retested-original-pair.png`。ファイル名と補足が近すぎた配置、一覧のホバー中に文字が白く消える不具合、図へのTab移動を修正した。停止位置の×、原本の=・≠・?、古い観測の破線と文言で、状態を色だけに依存させない。

関連検証は共有観測41、従来の観測24、共有アクセス投影21、診断61ケースが通過。Samba転送・失敗・再試行・保存再開は137チェックを通常と狭幅で通過し、サービス画面とエディター読込も通過した。旧2.2.0の実セーブのQAコピーは33項目を維持して再開でき、プレイヤー本体のSHA-256 `9ceabc887485dc835df3dec6e89b75c96a600025b54b4090d5b422e062c110f8` は変更前後で同一だった。

初見プレイヤーによる検証は行っていない。既知の部品にGodot入力を送る通し検証と、Windowsからの開発者手動プレイを区別する。起動時に外部画面取得が黒くなる既存問題は、[切り分け記録](startup-observation.md)の限界を引き継ぐ。

次の最優先課題は観測を古くする範囲。今回の実プレイでは共有のAvailable変更や別ファイルの保存だけでも、未変更の `partner-order.csv` の原本照合が古くなった。表示は既存の鮮度判定を忠実に示しているが、無関係な変更で再検査を増やしている。次のサイクルは現在の画面を再度プレイし、観測と変更対象の依存関係を狭められるか確認する。
