# 起動の描画と外部画面取得の切り分け

2026-10-05、ソース `3520e8e`、Godot 4.7.2、Windows・AMD RX 9070 XT。過去サイクルで起動時に観測した黒い画像を、製品側の起動停止と区別するために調べた。

- 通常のメインシーンは無入力のスモークで終了まで進行し、601ノード・32 FPS・245 draw callsを記録した。
- 同じメインシーンを読み込む観測用SceneTreeは、無入力で152描画フレーム・32 FPS。`frame_post_draw` の後に取得したroot画像にはタイトルとオフィスが表示された。25秒時点も789フレームで進行していた。
- 外部から取得したウィンドウ画像は、ゲームを前面へ出した後も黒かった。オフィス・Graphicsを外し、ColorRectとLabelだけを表示する最小シーンでも同じ黒画像になった。最小シーンも160フレームで進行していた。
- コマンド引数で一時的にANGLE/D3D11を指定しても外部の黒画像は再現した。ゲーム内部は136フレーム・29 FPSで正常画像を描画した。Shift入力でも外部取得画像が復帰し、Alt固有のゲーム処理は必要なかった。

画像取得はGodotの[推奨手順](https://docs.godotengine.org/en/4.7/classes/class_viewport.html)に従い、全viewport更新後の[frame_post_draw](https://docs.godotengine.org/en/4.7/classes/class_renderingserver.html)を待った。観測用スクリプト、無加工PNG、標準出力はローカル `artifacts/github-publication/audit/startup-surface-20261005/` に保存した。観測はQA専用保存先を使い、元プレイヤーセーブ・製品の描画設定を変更していない。ANGLEは製品の既定値へ採用していない。

この結果は、ゲームの読み込み・描画が停止しているという説明には反する。一方、内部root画像はWindowsの最終表示ではない。ウィンドウ表示・外部取得のどちらに原因があるか、実際の人の画面でも黒いかは未確定。黒い取得画像だけを根拠に、製品の起動コードや描画方式を修正することは見送った。「起動の黒画面を修正済み」とは扱わない。次の確認は同時刻の外部表示、無入力のwindow状態、利用者の実画面による切り分け。
