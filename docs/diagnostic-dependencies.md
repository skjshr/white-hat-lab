# 原本検査の現在性

開始時点は `4c1b1d3`。1280×720の通常GUIでDAY5の共有元を再開し、`partner-order.csv` の原本合格を確認した。Cockpitで共有のAvailableを変更して保存しただけで、未変更の原本まで「以前は一致」に変わり、合格数が3/6から0/6になった。今回の問題は、証拠と関係のない変更が再検査を増やすこと。

達成条件は、別の設定・別ファイルの変更では原本検査を維持し、対象ファイルの内容・存在・要求・受入条件が変われば古くなること。実測結果そのものは保存したままにし、変更後の結果はプレイヤーが明示的に測る。旧セーブの過去の結果を現在の合格へ自動昇格させない。

## 観測の依存範囲

VMが公開された `sha256sum` のコマンドを実行し、実際のSHA応答か対象ファイル不在の応答を得た後だけ、任意の `fingerprint_kind: local-file-v1` を測定レコードに保存する。指紋の対象はホスト、章、公開コマンドと期待、VMのパス規則で解決した対象、存在、実バイトのSHA。相対パスは作業ディレクトリの変更で対象が変わり、絶対パスは作業ディレクトリと無関係。

| 操作 | 原本検査 | サービス・アクセス検査 |
| --- | --- | --- |
| 共有の下書き保存・適用 | 対象の内容が同じなら維持 | 従来どおり再測定が必要 |
| 別ファイルの保存 | 未変更の対象は維持 | 従来の範囲で失効 |
| 対象の変更・削除・再作成 | 変更前の観測になる | 従来の範囲で失効 |
| 原本へ復元 | そのバイト列の検査がある場合だけ現在性を回復 | サービス状態は別検査 |
| 未接続・不正なコマンド | ファイルの観測を作らない | 従来の判定を維持 |

この変更は局所的な原本保全の証拠を維持するもので、共有への接続成功や納品合格を保証しない。受入判定は既存のサービス条件と、記録された各診断を引き続き要求する。描画・現在性の照会・再生はVMコマンドを実行しない。

未知の指紋種別、空の指紋、不正な対象は古い観測として扱う。旧レコードに種別がない場合は従来のVM全体の指紋を維持し、実際に再検査したときだけ新しい依存範囲へ移る。コマンド・期待の変更、リセット、バックアップの検査パス移行では測定の種別も破棄する。既存の測定保存トランザクションが、種別・指紋・観測・作業・現金を一緒に巻き戻す。

## 検証

記録は `../audit/diagnostic-dependencies-20261006/`。通常プレイの変更前画面は `01-before-original-fresh.png`、問題の再現は `02-before-unrelated-config-stales-original.png`。プレイヤー本体のセーブは変更せず、QAコピーで操作する。

`test_diagnostic_dependencies.gd` はVMフィクスチャと保存トランザクションを検証する。これは通常プレイの完遂証拠ではなく、内容・存在・要求・条件・相対パス・別ホスト・不正な種別・旧レコード・未接続・保存失敗と再試行の判定境界を確認するテスト。

判定境界の最終検証は43項目、失敗0。旧ホームの別名が実ファイルへ切り替わる場合、空のファイルと不在の違い、バックアップ検査パス移行で旧測定が消えることも確認した。関連回帰は診断スイート（標準36＋連携3案件を担当）、サービス監視44、支店監視34、業務データ74、バックアップ認可の案件53項目が通過。診断ログの `cases=61` は全カタログの件数で、全61案件をこのスイートが実行した意味ではない。終了時の保存失敗・再試行、セーブ回復、端末対応も通過した。旧2.2.0のプレイヤー本体のQAコピーは33項目を維持して再開し、本体のSHA-256 `9ceabc887485dc835df3dec6e89b75c96a600025b54b4090d5b422e062c110f8` は変わっていない。

`test_share_diagnostic_native.gd` は、公開キャリアAPIで通常資金のDAY5案件を受注する準備後、Godotのマウス・キー入力で共有の下書き保存と適用、別ソフトからの注文変更、原本復元と実測、他ファイルPUT、共有へのアクセス、受入確認、納品、請求、入金を操作する。共有の設定や他ファイルPUTの後も原本検査を維持し、実際の注文変更では注文原本だけが古くなって未変更の顧客名簿は合格を保った。画面表示・再生の純粋性、保存失敗の巻き戻しと再試行、UI破棄と保存再開も含む。

1920×1080・文字100%は4074チェック、454クリック、583キー、21スクロール、失敗0で完了した。原本へ復元した後に明示的な再検査を入れ、直前の不一致記録を勝手に合格へ変えずに他ファイルPUTの検証を行った。評価A、入金11880、経費700、純益11180、資金30014→41194、信用250→361、顧客満足70→75、会社レベル6→7を確認した。

960×600・文字130%は4089チェック、457クリック、583キー、28スクロール、失敗0で同じ納品・入金まで完了した。図と検査・詳細への導線、全オブジェクトと開いた証拠の可視範囲、Tab/Enterを確認した。選択色と見出しの仕上げ後は、この狭幅の通し検証と広幅の診断UI検証が通過している。

通し検証の途中で、古い結果を選択した行まで緑系に塗られて合格と紛らわしいことを見つけた。選択は診断ラボの紫系へ変更し、原本の見出しをファイル名と「原本照合」に短縮した。状態はチェック・×・↻と短い文言で区別する。

Windowsからの通常GUIでは、旧結果が自動で合格へ変わらず0/6のまま再開すること、明示的に原本を再検査して1/6になることを確認した。その後、別の共有設定を保存・適用しても二枚の紙は「一致」のまま残った。`04-manual-remeasured-current.png` と `05-manual-original-current-after-config.png` に記録し、新しい指紋種別と保存済みの測定をQAセーブで確認した。

通常終了・再起動後にも一致と保存済みの合否が残った（`06-manual-resumed-current-original.png`）。手動プレイの範囲は共有設定と原本確認で、案件全体の納品・入金は上記のGodot入力による通し検証である。

初見プレイヤーによる理解・面白さの検証は未実施。通常GUIの手動操作と、Godot入力による案件全体の通し検証は別の証拠として記録する。

次の最優先課題は通常起動の表示。今回も起動直後の外部画面取得が黒く、Shift入力後にメニューが現れる挙動が再現した（`03-manual-startup-black.png`）。描画・フォーカス・外部取得のどこに原因があるかは未確定で、[既存の切り分け](startup-observation.md)も参照する。次サイクルは現行版を起動して再確認し、入力を前提にせず開始画面を確認できる状態を調べる。原本以外の診断は現在も従来のVM全体の依存範囲を維持している。

同じQAプロファイルの再起動では入力前からメニューが見える場合もあった。黒い画面がプレイヤーの実画面にも生じているかは、この外部取得だけでは確定しない。
