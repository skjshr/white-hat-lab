# 共有案件の最初の一周

起点は作業ブランチ `d64c162`。新規会社を作り、Outwatchでつばさ文具の依頼を受注し、Cockpitへ接続した。社員の保存失敗・来客への公開という症状を確認するには、共有編集から利用者の入力フォームへ移り、操作とパスを指定し、下へスクロールする必要があった。通常の一覧画面から影響を見渡せないことを今回の最優先課題とした。

単一共有のホームを、社員・来客の端末と共有フォルダーがつながる作業面にする。読む・保存する操作は既存の実診断を一度だけ実行する。設定を直す判断はプレイヤーが行う。手動のアクセスフォーム、複数共有、構成編集は引き続き利用できる。

達成条件:

- 未測定、実際の許可・拒否、通信等のエラー、古い測定を形と短い名称で区別する。
- 操作成功と依頼条件への適合を区別する。来客が読める状態を安全な成功として表示しない。
- 保存だけでは適用中の動作が変わらない。設定や共有データ変更後は再検査が必要。
- 同じ作業面で再試行できる。保存失敗はVM・測定・工数・時計を巻き戻し、古い結果で成功を装わない。
- 受注から修正・再検査・納品まで実入力で進め、報酬・顧客評価・次の相談を確認する。
- 中断と保存再開で実測・下書きが残る。既存セーブに新しい測定義務を追加しない。
- 1920x1080と960x600・文字130%で主要操作へ到達する。色だけに頼らない。

## 実装と検証結果（2026-10-05）

既存の共有ホームを作り直した。社員・来客の端末、閲覧・保存の書類操作、実際の共有フォルダーを配置し、許可は矢印、拒否は交差印、未測定は破線、古い測定は時計で表示する。通信失敗と権限による拒否を区別し、依頼条件に合っているかは別の印で示す。設定値から結果を推測せず、既存VMに記録された実診断だけを使用する。

各操作は既存の診断を一度だけ実行する。社員の保存は実ファイルを転送し、共有の変更で古くなった測定は再検査になる。保存に失敗した操作はその場に「保存失敗」を表示し、以前のVM・測定・工数を保持する。再描画後のキーボード選択も保持する。既存の設定フォーム、設定ファイル、手動アクセス、ファイル管理へ移動でき、Sambaタブで作業面へ戻れる。セーブ形式と納品条件は変更していない。

検証は通常プレイヤーの保存と分けたQAプロファイルで行った。ログ・画像はチェックアウト外の `../audit/share-20261005/` に保存した。

## 次の最優先課題

通常起動の初期画面が黒いままになる現象を2回観測した。最大化で表示が回復し、その後の3回目は通常起動で表示された。この共有作業面サイクルでは起動経路を変更していない。後続の小さい変更で初期描画処理を修正し、通常起動3回と保存案件再開を確認した。検証範囲と再発・別GPUの限界は [startup-surface.md](startup-surface.md) に記録している。

次は、受注済み案件を続けられない場合の契約上の中止・顧客との再調整。現状の画面中断は作業を保持するが、明示的な案件辞退とは異なる。失敗の履歴と顧客評価、再挑戦の入口をつなげる必要がある。
