# 納品から顧客の返答へ

## プレイで見つけた問題

最新の `329932b` を取得し、前サイクルで実際に入金した会社を通常GUIで再開した。日報の案件は納品・入金済み、満足75→60、次の相談は保留。それでもOutwatchの本文は「日報を保存できず、締めが止まっている」という受注時の事情だけだった。状態名と本文の食い違いを今回の優先課題にした。

達成条件は、依頼と納品後の返答を同じ案件の会話として読めること。実際の納品が確定するまで返答を出さず、確認内容・納期・顧客評価・次の相談がその案件の保存済み結果と一致すること。添付確認から顧客の次の仕事と精算へ移動でき、戻った際の選択とセーブ後の再開を保つ。960×600・文字130%でも主要操作を隠さず、過去の案件や旧セーブに新しい測定を捏造しない。

## メールとしての作業面

[Outlookの一覧と閲覧ペイン](https://support.microsoft.com/en-us/outlook/mail/change-how-the-message-list-is-displayed-in-outlook)と[Gmailの会話表示](https://support.google.com/mail/answer/5900?hl=en)を参考に、受信トレイ、送信元、返答、添付、折りたたんだ元の依頼をつないだ。小画面は一面、広い画面は一覧と本文を並べる。資料を直接移すエクスプローラーの二面配置とは役割を分ける。

納品後は受取確認の紙、時刻、評価の前後の棒、次の相談を同じ縦の線に置く。✓／?、期限内／期限超過、75→60、Ⅱ相談保留など、色以外でも状態を読める。問い合わせの原文と保存した確認内訳は必要なときに開く。受取確認・顧客との仕事・精算の操作はメール下部に固定し、本文の長さで主要な操作を押し出さない。

「顧客との仕事」は、その顧客の実際の相談IDを選んで会社画面を開く。返答に表示する相談は納品時の保存済みイベントであり、会社画面は現在の相談状況を表示する。過去の返答を現在の状態に書き換えない。現在の案件だけに精算への操作を出し、過去の添付から別の案件の精算を開かない。

## 情報源と保存

返答はゲーム内の顧客反応を、正確な契約IDの納品履歴・合格した確認内訳・納期区分・評価の前後・顧客イベントから表示するもの。独立したメール配送や顧客操作をシミュレートしたとは扱わない。読んだときに測定・決済・顧客評価の更新・作業時間の加算は行わない。転送が成功しただけでは納品後の返答を出さない。

日報の再開は、案件名だけから推測しない。以前の同名案件は別の資料を扱っていたため、社員の実際のPUTが `/srv/data/report.txt` を送り `putting file report.txt: OK` となった保存済み応答がある場合だけ、日報の確認を表示する。確認内訳や評価、納期、応答のない古い履歴は、その情報を不明として残す。カタログの現在の条件で埋め直さない。

納品時の既存の `delivery_results` を、その契約の履歴にも保持する。追加の測定はせず、日締めで配車用の契約コンテキストが退役しても、納品時の観測が残る。旧履歴にこの項目がない場合は、同じ契約ID・顧客・案件の保持済み精算記録がある場合だけ利用し、最新の別案件の精算から借りない。セーブの版を変更せず、古い観測を後から追加する移行も行わない。

会話の選択は件名に加えて契約IDを保存する。履歴閲覧は作業中の契約を切り替えず、同名の過去案件にもそれ自身の確認内訳と評価を表示する。検索は元の依頼と返答の両方を対象にする。

納品時には、その案件の依頼本文・件名・送信元も控えとして履歴に保存する。進行中のメールと同じ元データを使い、通し操作で実際に読んだ本文との一致を確認する。将来のカタログ更新や日締めで書き換えない。旧履歴にメール本文がなければ、その契約に残っている受注時の業務説明を「依頼の控え」として示す。どちらも残っていなければ本文の記録なしとし、現在のカタログから原文を再生成しない。

## 検証と限界

経営の通しプレイは、実際に納品・入金したDAY6の会社から自然に出現している日報案件を受注する。見積拒否、下書き再開、受注保存失敗、実キーでの編集、権限拒否、誤った来客公開、納品拒否、修正、保存失敗のロールバック、再試行、納品、顧客の返答、顧客との次の仕事、精算、入金、結果再開を通す。資金・技能・市場・正解設定・納品結果を注入しない。背景時計を止め、明示的な作業時間と経費は残す。

短い対応で期限内に納品する経路も別に通し、評価上昇と相談の返答が遅延経路と異なることを確認する。履歴閲覧、検索、旧情報欠落、描画の不変性、実際の日締め後の履歴については、実プレイ原本を複製したUI/APIフィクスチャで確認し、通し入力の証拠と区別する。

初回のUIフィクスチャは大きい論理画面を縮小してしまっていたため、文字130%の証拠に使わない。通常起動と同じGraphics設定と実ウィンドウ座標を適用すると、紙と操作が下に隠れる問題が現れた。余白と紙の高さを調整し、操作を下部に固定して修正した。通しテストの納品後確認は非同期で行うため、テスト側の呼び出しもawaitし、スクリプトエラーを終了コードだけで見落とさない。

既存の `test_software_fidelity.gd` と `test_company_workflows_ui.gd` にも、ウィンドウサイズだけを変え、Graphicsの内部座標を適用していない箇所があった。前者は狭い一覧の判定に失敗し、後者は設備選択のクリックが別の位置へ送られて後続処理も止まった。通常起動と同じGraphics設定を使い、実際の論理幅960を確認するよう修正した。テストの期待値は緩めず、進行中の本文・再開・管理と会計の既存操作を確認した。

初見の第三者による理解・楽しさは未検証。[起動時の外部画像取得の暗転](startup-observation.md)の原因についても、以前の観測の限界を維持する。

次は、返答から通常依頼の再受注と顧客の信頼回復まで実際に進め、次の仕事へつながるところで最も体験を損なう箇所を選ぶ。
