# 納品から次の顧客業務へ

今回の単位は、新支店の三サービス復旧を納品し、同じ顧客の受注表退避を受注・復元・納品するまで。一般の依頼一覧へ戻るだけだった流れを、顧客の関係図と実資料の引き継ぎでつなげた。

## 達成条件と画面

- 顧客を切り替えると、前の納品物、保存した顧客満足の目盛り、次の仕事が一つの図に出る。
- 期限内の納品、準備待ち、相談保留、対応済みを、印・時計・停止記号・実線と破線でも区別する。
- 紙と目盛りを選ぶと記録・条件が開き、次の業務を選ぶと実際の準備・翌日営業・見積・関係回復へ進む。詳細は第一画面から外す。
- 次案件は前回の顧客ファイルの実バイト列を使う。単なる共通サンプルへの差し替えで合格させない。
- 処理成功、顧客の受入判定、入金を区別し、失敗と再試行、日締め、保存後の再開でも結果が残る。

CRMの顧客切替と履歴・関係指標には、[Dynamics 365の関係分析](https://learn.microsoft.com/en-us/dynamics365/sales/relationship-analytics)と[顧客の履歴](https://learn.microsoft.com/en-gb/dynamics365/customer-insights/journeys/timeline)を参照した。レイアウトはゲーム独自。メールの受信箱、紫のERP、黒緑のBackrest、クリーム色の精算書と区別し、CRMは横方向の関係図と顧客切替を使う。

## 引き継ぐ案件

「新支店の受注表を別拠点へ退避」は、北斗物流・新支店の業務再開後の別業務。運用スキルを獲得し、通常の翌日市場の相談枠から見積を送る。信用不足や期限超過で保留された相談は、通常案件による回復が必要。相談のために枠・資金・スキルを強制的に追加しない。

前回の納品履歴と保存した共有サーバーの `/srv/share/partner-order.csv` を読み、**受注時に一度だけ**退避対象 `/srv/data/partner-order.csv` と顧客の照合値を保存する。日締めで片付けられる案件一覧を出典にしない。ファイル欠落・評価記録欠落なら代用品を作らず、受注を成立させない。取得と描画は旧データを更新しない。

毎日の offsite 退避、実際のスナップショットからの復元、引き継いだ内容の照合、原本と他資料の保持を別に検査する。[resticの復元](https://restic.readthedocs.io/en/stable/050_restore.html)のように、保存版と復元先を分ける。Backrestで紙と復元先のトレーを選べる。ゲーム内で完結し、実サービスへの接続や契約は発生しない。

## 検証と限界

`test_customer_continuation_native.gd` は、通常資金で自然に出たDAY 5の新支店案件を使う。最初の受注準備だけ公開API。三サービスの修復、誤ったデータ、原本への戻し、検証、納品、請求、顧客切替、獲得済みポイントでの運用スキル投資、実際の日締め、次案件の見積・受注、復元・再試行・二度目の納品・入金はGodotのマウスとキーで操作する。3Dオフィスを省いたInterfaceなので管理画面の入口だけUI APIを使う。背景時計を止め、操作費用は残す。

復元先を `/tmp` にすると処理は成功して実ファイルも生成されるが、顧客の指定先ではないため受入判定は失敗する。その後 `/restore` への再対応、保存失敗によるロールバック、再試行、納品前の中断・保存再開を確認する。`--late` は実際の日締めで前の納品を遅らせ、顧客満足の低下と次の相談保留を調べる。

`--continuation-only` は今回の実入力で納品したチェックポイントからの修正用再開。最初からの通しプレイとは別集計。`test_branch_handoff.gd` の追加行・別金額は合成のVM検証であり、通常プレイの成果とは扱わない。旧セーブの相談・成功評価を後付け生成しない。過去の実納品と資料が揃う旧セーブは、翌日の通常市場から新案件へ進める。

通常の3Dオフィスから開いた960×600・文字130%では、最初の独立Interface検証と表示領域の大きさが異なることが分かった。テスト側にも通常オフィスと同じ `Graphics.apply_settings` を適用し、物理・論理の両方を960×600に揃える。最初の独立Interfaceで通った狭幅検証を、この実画面の証拠には使わない。

この条件で顧客の図の長い案件名と補足が重なったため、図の高さ、折り返し位置、補足の位置を修正した。通信ルール一覧の再検証では、検証側が縦スクロールしない内側の表の画面外中心へホイールを送っていた。表示内の縦スクロール領域に実入力を送るよう直し、描画領域・文字の大きさやゲーム内状態を緩和せず再確認する。

長くなる狭幅の納品記録閲覧では、デスクトップの通常の自動保存が「診断」から「納品」へのウィンドウ切替を記録した。差分を保存して調べ、変わった項目が画面の `active_app`、`windows`、`maximized`、`open_apps`、`running_apps` だけであることを確認した。閲覧中の比較からこの5項目だけを除外し、資金・履歴・顧客評価・相談・VM・ファイル・測定・編集中内容・保存済み応答など残り全体を照合する。直接の描画呼出しでは自動保存が動く前の全状態一致も検査する。自動保存を停止する修正はしていない。

日締め後に開き直した遅延経路では、切断済み閲覧者の書込可否を含む現在のブラウザー表示と、前の自動保存に差が残っていた。読取専用の閲覧検証を始める前に、現在のUIを通常のセッション保存で確定する。取得や測定は実行せず、この保存で資金・履歴・顧客評価・納品結果が変わらないことも検査する。保存済み応答を比較対象から除外する方法は使わない。

ERPの紙のツールチップも画面の子Labelとして現れ、単一行の図中ラベル検査に混入する場合があった。図の実際の名前付きラベルを検査対象に直し、折り返して表示する詳細ツールチップと区別した。元の失敗ログ・画像・状態差分は残す。

通常GUIのクリックでは、紙を押して詳細が開いても、下の画面外にあるため変化が見えないことを確認した。詳細を開くと表示をその記録へ移し、「記録を閉じる」にフォーカスを置く。閉じると、押した図形のフォーカスと図全体の表示に戻す。ネイティブ検証も単なる `visible` 判定から、詳細の実表示領域、余分なスクロールの不要、閉じた後の図全体・フォーカスの確認へ追加した。

自動入力と開発者のGUI操作は、初見プレイヤーの理解や面白さを立証しない。会社画面の全領域を図に作り替えたわけではなく、成長目標・運営と新規顧客の入口は引き続き改善対象。

## 保存された実プレイの成果

元ログ・PNG・操作記録・完了セーブはローカル `../audit/customer-continuation-20261006/` に保存した。最終の実オフィス縮尺での狭幅通し (`native-office-narrow-release`) は **1,757確認・209クリック・609キー・63スクロール、失敗0**。初回の支店修復から、実際の日締めと次の依頼の受注、誤った復元先、保存失敗と再試行、納品前の保存再開、二度目の納品・入金・顧客の結果確認まで通した。

同じ実オフィス縮尺の狭幅で、実際の日締めにより前の支店納品を遅らせる経路 (`native-office-late-final`) も **1,493確認・169クリック・574キー・55スクロール、失敗0**。評価Aでも顧客満足は70→55、次の退避相談は保留となり、受注資格がないまま保存再開された。図は期限超過の印、55の目盛り、破線、保留記号で表した。この経路の後には読取専用チェック開始前の通常UI保存も加えているため、先の通し検証とは確認数が異なる。

詳細の表示移動を直した後は、実入力で完了した上記の初回納品セーブから継続案件を再操作した。`continuation-office-narrow-inspector` と `continuation-office-wide-inspector` はそれぞれ369確認・失敗0。両方で準備待ち、相談受付、対応済みの図、実ファイルの退避・復元と入金、詳細が操作後すぐ見えること、閉じた後の図全体とフォーカスを確認した。実際の遅延完了セーブからの保留図 (`continuation-office-paused-inspector`) も52確認・失敗0。これらは初回受注からの通しではなく、修正した継続部分の再検証である。

関連モデルは顧客循環190確認、顧客UI140確認、資料引継ぎ17確認、退避受入91確認、退避受入のGame統合53確認、退避作業台100確認で失敗0。顧客循環のモデル回帰には、相談を完了した後の別の納品でも最新の満足記録を保持し、過去の対応済みを取り消さない条件を追加した。対象組合せを除くVM回帰は38件・失敗0（対象組合せ24件は除外し、今回の動的な引継ぎは上記の通しと専用検証で確認）。旧2.2.0プレイヤーセーブのQAコピーは33確認・失敗0で再開と保存往復を維持した。元のプレイヤーセーブと受注前のDAY 5キャリアのSHA-256は不変。

## 次の優先課題

新規受注の第一画面で、依頼の対象・利用者・停止すると困る業務を見せること。継続顧客の関係図はできたが、初回の依頼はタイトル・金額・文章の見積へ移る。次は初回の一件を対象に、受注前の影響範囲と復旧後の利用を視覚的につなぐ。

他顧客への切替では、退避以外の次業務に汎用の図形と「次の業務」が残ることも確認した。機材調達などの対象の造形は、次の受注画面との統合で優先して具体化する。
