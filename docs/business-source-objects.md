# 顧客業務の取得対象を操作する

開始時点は `7c9408b`。現行版を通常GUIで再開し、DAY5「支店の業務再開」の販売・会計を操作した。従来の共有元欄は、小さなアイコン、文字三列、矢印で構成され、接続・資料・業務のどこで止まったかを文章から読む必要があった。変更前の元画像はローカル `../audit/branch-ledger-20261006/01-sales-before.png` と `02-accounting-before.png`。

今回は顧客ERPの「実共有元→資料→業務結果」を、一つの取得応答として調べられる単位で改善する。達成条件は、サーバー・CSV原本・業務の対象が見えること、接続失敗・資料不足・読取成功後の形式異常を別の停止点で示すこと、対象の選択で保存済みの証拠を確認できること、再取得・業務の修復・納品は明示操作で行うこと。

## 造形と観測

既存の紫のERPナビとレコード操作を維持する。[Odoo Salesの見積・受注・請求の業務構成](https://www.odoo.com/documentation/19.0/applications/sales/sales.html)を参照する系列であり、実製品の全機能を再現するものではない。Cockpitの管理枠、監視の設備配置、診断の照合台とは目的を分ける。

三列の説明を、ラック、折り返しのあるCSV紙面、業務の帳票へ置き換えた。販売は受注票、顧客は連絡先、会計は開いた帳簿。業務の件数は取得応答の実レコード数で、描いた行は件数の縮約表現である。図の線は取得応答の依存関係を示し、物理配線やパケットの流量ではない。

- 実線と矢印は確認できた取得区間。
- 切れた線と×は接続・資料・業務利用の失敗。
- 破線と空の紙面・帳票は、下流が未確認であること。
- ✓・×・!・?と短い状態名も併記し、色だけに依存しない。

共有に接続できても注文金額が壊れている場合、サーバーとCSVは読取成功を保ち、受注票の手前で停止する。会計が要求する `ledger.txt` の欠落は、注文原本の欠落と混同しない。資料不足の応答だけで、注文と顧客のどちらが消えたかを断定しない。

全て「前回の取得」の表示。別ソフトの変更を描画で再取得しない。各対象はマウスまたはTab/Enterで選べ、その対象の詳細と実際の取得応答を開く。原文のAPI応答には共有設定のメタデータが含まれる場合もあるため、主画面の対象ファイルと原文を分けて扱う。図の表示・選択は設定、ファイル、測定、作業時間、現金を変更しない。追加のセーブ項目や既存記録の置換はない。

## 検証方法

`test_business_source_native.gd` は、実際の通常資金のDAY5キャリアをQA専用にコピーし、公開APIで自然に出た案件を受注する準備後、Godotのマウス・キー入力で通信・共有を修復する。保存失敗と再試行、Nextcloudからの不正な金額の提出、台帳の形式異常、実世代の復元、再取得、顧客・会計の別資料、UI破棄と保存再開、三台の診断、納品、請求確定・入金まで操作する。背景時計だけを止め、操作の作業費用を残す。対象を選択して原文を開いてもGameとVMが不変であること、対象・名称の幅、拡大文字、Tabの可視性も検査する。

通常GUIの手動操作、自動入力による案件全体の通し検証、合成応答を使う部品検証は別の証拠として扱う。初見プレイヤーによる理解・面白さの検証は未実施。

最終のログ・元PNG・操作記録はローカル `../audit/branch-ledger-20261006/`。`wide-release3`（1920×1080・文字設定100%）は1243確認、144クリック、537キー、21スクロール、失敗0。`narrow-release`（960×600・文字設定130%）は1253確認、146クリック、537キー、24スクロール、失敗0。両方とも保存再開後の証拠表示とTab/Enter、三台の実診断、顧客結果、請求・入金まで完了した。最終ログにスクリプトエラーはない。

両サイズで評価A、請求 `INV/0005` の入金11880、経費700、純益11180、資金30014→41194、信用250→361、顧客満足70→75を保存データでも確認した。`completed-wide.json` と `completed-narrow.json` に完了セーブを別々に残した。

通し検証で、詳細が伸びた後にTabの対象が画面外に出る不具合を見つけた。対象と主要ボタンに、配置が確定した後のフォーカス表示を追加した。画面再構築で部品が解放されても遅延処理が参照しないよう修正した。失敗ログも残し、最終の通し検証をやり直している。
