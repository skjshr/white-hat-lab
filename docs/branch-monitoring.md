# 支店の3台を見失わずに対応する

2026-10-05。「支店の業務再開」を受注から入金まで確認する限定サイクル。全ソフトや全案件の改善完了を示すものではない。

## 実プレイで選んだ問題

最新の作業ブランチをfetchし、HEADとoriginが `bf87c4b`、差分0であることを確認して開始した。前サイクルで通常の日締めから得たDAY5の受注前コピーを別のQA保存先で開き、標準見積¥10,800の支店再開を手動受注した。注文APIの診断は通信拒否で失敗した。共有サーバーへ対象を切り替えると、その失敗と他の2台が監視画面から消えた。共有側ではプロセス稼働だけが見え、どの業務に影響しているかを辿れなかった。

手動操作後の `accepted-with-failed-orders.json` はSHA-256 `c5d086ba1b523beca41995382001ad16ea2f97ef88335883ca328e51467bec51`。実キャリアから受注・接続・失敗診断を行った保存であり、資金・技能・正解設定の注入はない。完了検証のコピーと区別し、未納品のまま保持する。

達成条件は、対象を切り替えても3台の記録と失敗が残ること、共有資料の変更によって他端末の測定が古くなること、再診断で現在の結果へ更新できること、図の表示と対象選択だけで接続・修復・測定が起きないこと、保存失敗の再試行・中断・既存セーブを保つこと、960×600・文字130%でも納品と入金まで操作できること。

## 監視だけに必要な形

監視の支店案件画面を、端末ごとの放射図から顧客全体の接続図へ置き換える。共有資料を中央に置き、左の受注サイトと右の外部共有へ分岐する。実装上の依存はSamba→業務APIとSamba→ポータルであり、ゲートウェイ→ポータルという架空の経路は描かない。

図形には実ホスト、プロセス稼働・停止、未適用構成、受入の件数を置く。共有側は実ファイル `customers.csv` と `partner-order.csv` の保存状態を表示する。ファイルの存在・プロセス稼働と、業務が利用できるという受入判定は分ける。線は受取側で実測した注文API・資料取得の状態を使い、✓・×・↻・○・？で色以外でも判別する。未接続のポータルに正常状態を作らない。

対象の図形や線を選ぶ操作は監視内の選択だけを変える。「選択した検査へ」「サービス制御」で明示的に実端末へ移る。測定の応答・履歴は必要なときに開く。VMの状態取得は保存済みまたは一致する稼働中のschema 2記録をコピーして計算し、未記録端末を初期化しない。描画はGame・VM・測定・時間・資金を変更しない。既存の保存形式を増やさず、監視の選択は既存デスクトップセッションに保存する。

メールは受信箱、Odoo風の業務画面は紫の台帳と共有元の流れ、Sambaは共有設定、pfSenseは通信ルール、Nextcloudは資料・世代比較、監視は青い接続図と実測を担う。同じ一覧画面へ揃える変更は行っていない。

## 検証の方法と限界

同じ受注前の実キャリアをQA保存先へコピーする。公開APIで自然に出た案件を受注した後、実Godotのマウス・キー入力で通信拒否の診断、通信ルール修復、共有保存の失敗・再試行、共有再開、注文取得、別ソフトから不正金額の保存、測定の失効と再診断、世代復元、顧客と会計の参照元、中断保存・再読込、3台の診断、納品、顧客評価、請求確定・入金へ進む。図形の選択、Enterでの選択、端末切替の保存失敗・再試行も含む。元キャリアはバイト単位で不変であることを検査する。

最初のネイティブ画像では資料名が端末図形の下端へはみ出した。図内のアイコンと余白を詰め、ラベルの実寸幅・一行表示・図形内の縦位置も検査対象に加えた。単にテスト成功を楽しさや直感性の証拠にはしない。初見プレイヤーは参加しておらず、既知の操作対象を使う自動入力と開発者の手動操作による確認である。

端末を移動した際に、移動先の保存済み監視画面が別端末の選択を復活させる混乱も見つかった。明示的な移動後は移動先を選択して表示し、保存・再開もその選択を保つよう修正した。監視内で別の図形を選ぶだけの場合は接続先を変更せず、上部には現在の接続先、図の下には選択した対象を表示する。
