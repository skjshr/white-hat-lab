# 日報の受注と共有復旧

## 今回の問題と達成条件

前回の機材導入から実際に納品・入金したDAY6の会社で、新規相談「社員が日報を保存できない」を受注した。通常GUIの960×600・文字130%では、受注詳細はタイトル・料金・閉じた依頼説明が中心だった。作業PCのCockpitで社員の保存を試すと実際に拒否されたが、検証対象は日報ではなく `orders.csv` だった。

今回の単位は、経理の日報保存を復旧し、来客への公開を防いだうえで納品・入金する仕事。受注時に利用者・対象・困っている操作・守る境界を示すこと、実際の日報ファイルが変わること、社員の保存成功だけでは納品できないことを達成条件にした。

## 画面と操作

営業ソフトでは、経理の日報から社内共有への保存が止まっている作業票を表示する。資料、保存の切断、共有フォルダー、鍵、来客との境界で構成し、機材案件の紺色の導入設計図とは色・形・配置を変える。日報と来客の対象を選ぶと補足を開ける。申告と納品条件は未調査・未検証の表示であり、VMの初期設定や未実行の測定を成功・失敗の証拠として表示しない。

価格は営業ソフト共通の顧客予算・相場・利益のものさしを使う。提示額、保存・送信、予算と赤字の状態は既存の金額計算につながる。実際に予算を超える見積は不成立になり、送信失敗は入力を残して再試行できる。

新しく受注した日報案件では、社員の本日分 `/srv/data/report.txt` と共有先の前日分 `/srv/share/report.txt` が別の内容を持つ。社員の保存検証は本日分を共有へ転送する実際のSMB PUT。Cockpitのフォルダーも日報の対象を表示する。社員を通し、来客を通す誤対応では保存自体が成功して日報が更新されるが、来客の閲覧検証が不合格になり納品できない。来客を拒否して再測定すると納品でき、別ソフトの結果・請求にも反映される。

Sambaの測定保存失敗は、公開APIが返す既存の日本語のロールバック応答も認識する。以前の保存済みの観測を維持して、操作の失敗を隣に表示する。同じ操作で保存できた場合は、直前の失敗通知を「測定を保存しました」に置き換える。測定結果の許可・拒否と、納品条件に対する合格・不合格は別の表示を維持する。

構成の参考は、依頼と作業を結ぶ [ServiceNowの作業指示](https://www.servicenow.com/docs/r/field-service-management/work-order-management/configure-work-orders.html) と、共有管理を別の管理ソフトとして扱う [Cockpitのアプリ構成](https://cockpit-project.org/applications)。画面の複製や外部サービスへの接続は行わず、ゲーム内の資料と状態で作業を表現している。

## 検証と互換性

記録は `../audit/ordinary-intake-20261006/`。`native-narrow-final` は通常オフィスと同じ表示処理で960×600・130%、`native-wide-final` は1920×1080・100%。両方で320確認、50クリック、64キー、不合格0。スクロールは小画面22回、広い画面2回。自動入力の経路数であり、初見プレイヤーの操作量を示すものではない。

本当にプレイした前サイクルの完了セーブから開始し、既に存在する通常相談を選んだ。資金・技能・案件の出現・設定の答えは上書きしていない。受注から誤対応、検証による納品拒否、誤対応後の中断・保存再開、修正、保存失敗のロールバックと再試行、納品、請求入金、成果の保存再開まで実際のGodotマウス・キー入力で進めた。背景の作業時計だけを停止し、明示的な作業時間と経費は加算される。

実際の結果は基本料¥3240、期限内加算¥324、経費¥700、純利益¥2864。現金は¥55964から¥58828、つばさ文具の満足度は75から80へ変化し、`INV/0008` を入金した。結果は各最終フォルダーの `completed.json` に残る。失敗履歴・VM観測・原本と共有先の実データも保存対象。

関連確認は既存共有投影21確認、市場UI、経済、日報互換15確認、実プレイヤーセーブ33確認で不合格0。日報の互換確認には、実装前に通常GUIで受注・調査したセーブを使い、受注済みの元の検証対象 `orders.csv` とファイルを保持した。既存契約に新しい本日分の日報を追加せず、新しい受注だけが新しい資料と検証を使う。実プレイヤーの保存元SHA-256は `9ceabc887485dc835df3dec6e89b75c96a600025b54b4090d5b422e062c110f8` のまま。

既存のチュートリアル共有案件も960×600・130%の実入力で受注・拒否・修正・保存失敗・再開・納品まで進み、199確認、24クリック、4キー、12スクロール、不合格0だった。

図の対象はTab・Enterで選べる。選択・ホバー・押下の文字と背景のコントラストを確認し、全対象・補足・価格の指標・固定操作・失敗表示のクリッピングを検査した。状態は×・○・鍵・破線と許可/拒否/再検査等の語でも示し、色だけに依存しない。

初期の失敗ログは残している。変数名衝突による読み込み失敗、ボタンの選択文字が白くなる問題、測定保存失敗の表示漏れを修正した。旧セーブ比較は同じケースの過去契約を誤って選んだため、現在受注した契約のVMキーを使って比較し直した。コントラスト判定はsRGBの線形化を使う計算へ修正した。

## 限界と次の課題

通常GUIの改修前受注・保存拒否の操作と、改修後の受注画面の目視・操作を記録した。通しの納品・入金は開発者の自動入力による確認。初見の第三者プレイヤーは未検証であり、「面白い」「直感的」とは判定していない。通常起動直後の観測で空の画面になり、Shift入力後に描画された現象も再現している。原因は未特定であり、今回の修正で起動問題が解消したとは扱わない。図の作業票は今回の日報案件に限定される。他の通常案件とメールの受信一覧はまだ文字中心の部分が残る。

次は実際に日報を開く通常業務をプレイし、顧客が使っているファイルと保存結果がエクスプローラーや編集ソフトから分かるかを優先して確認する。診断結果の合否だけで仕事が終わって見える部分を、利用者の作業と成果物から改善する。
