# 顧客の業務と復旧結果をつなぐ2案件

対象は、院内の業務一覧を開けない通信案件 `service-2-case-0` と、破損した台帳を別場所へ復元する `service-1-case-3`。既存の業務アプリ、pfSense風設定画面、Backrest風復元画面、診断と納品を利用する。新しい初回案内や別ダッシュボードは追加しない。

## 通信復旧

依頼は、港町クリニックの事務担当が法人向け請求の確認に使う一覧を開けないという症状から始まる。同じ `/sales` を再確認し、実際の業務データを取得できることと、外部の管理接続を拒否することを区別する。

名前解決やTLSで停止した要求にはHTTPステータスを付けない。データの形式不正など、アプリが実際に応答したエラーにはHTTPの結果を表示する。LANのIP通信がルールを通っても、それだけで業務一覧の復旧とはしない。

代表案件の業務画面には、同じ要求を明示的に検査する操作と、既存の通信設定へ移動して元の業務へ戻る経路がある。検査は実コマンドと応答、対象、設定・データの指紋、ゲーム内時点を記録する。閲覧・再描画は観測や工数を増やさない。変更後の古い結果は再確認が必要と表示する。保存に失敗した場合は観測、VM、工数と時計を戻す。

保存済みの設定と適用中の設定は別である。保存だけでは故障した業務要求は直らない。適用後に同じ要求を検査し、業務データの取得と管理接続の拒否を確認する。新規の代表案件では、既存の業務診断も実データの `/api/business/orders` を検査する。一般的なトップページの200だけで壊れた一覧を合格にしない。既存診断から検証・納品できるため、新しい欄の操作を必須の追加手順にはしない。

新しい観測欄は代表案件に限定する。承認済み保守など、業務通信を意図的に止める別案件にこの復旧条件を流用しない。既存の業務データ編集機能も維持する。実装していないデータ変更禁止や停止時間の制限を依頼文に付け加えない。

## 台帳復旧

最新の保存には破損した台帳が含まれる。保存版の内容と正常時の照合票を調べ、正常な版から `/restore` 配下へ復元する。台帳を本番へ置き換える権限は、この単体案件にはない。元の台帳、顧客台帳、受注表を保ったまま、復元先の内容を顧客へ引き渡す。

新規案件では、初期化時に保全対象の存在とSHA-256、必要な復元内容、承認された復元領域を独立した記録へ保存する。合否は復元内容の一致、原本保全、対象外データ保全を別々に確認する。変更したデータを元に戻して再検査すればやり直せる。ロード時に現在のファイルを新しい保全基準として採用しない。

実際に書き込んだ復元ファイルごとに保存ID・復元先・内容の出所を記録する。別ファイルを後で復元しても、その直近の保存IDを台帳の採用元として表示しない。照合票のパスも実際のv2復元先に合わせる。

Backrestでは、保存版とファイルを選んだ後は一覧を畳み、選択パス、保存内容、稼働中または復元先の内容、復元計画を近くで確認できる。版の切替で古い計画を無効にし、実行直前にも計画と現在状態を照合する。コマンドの実行成功や2ファイルの一致と、顧客の受入条件を満たしたことを区別する。存在しない取得日時は創作せず、保存順を表示する。

## 既存保存と他案件

| 状態 | 扱い |
|---|---|
| 新規の単体台帳復旧 | 保存済み保全基準を使う。既知の記録が欠けたり不正なら合格扱いしない |
| 保全基準が存在しない既存台帳復旧 | 元の判定を維持し、保全基準がないことを表示する。過去の原本状態を推測しない |
| 本番置換を承認した既存の複合復旧 | 契約作成時に `production_replacement` として区別し、単体案件の原本維持条件を継承しない。実本番データの復旧を既存の連携診断で検査する |
| 受注済みの通信案件 | 保存済み診断を維持する。新しい診断内容で既存契約を無断に厳格化しない |

ゲーム内の架空ローカル環境だけを扱う。実製品の全機能、実ネットワークやOS、顧客への聞き取り分岐、停止時間の合意モデルを完全再現するものではない。今回の検証は自動化した実画面操作とモデル・保存の検査であり、人間による楽しさや学習効果の評価ではない。
