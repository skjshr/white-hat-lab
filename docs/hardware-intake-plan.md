# 機材導入案件の受注設計

2026-10-06。既存の作業ブランチ feature/pentest-portal-workspace。

## 今回の体験と達成条件

前回納品後の DAY 06 を実際に再開し、「業務台帳の自動保存設定」の見積画面を操作した。資料、機材、復元先が画面に存在せず、必要・不足・追加発注が文章の一行に並んでいた。依頼詳細を開くまで、何を導入し、何を戻せれば納品できるか見えないことを今回の問題とした。

改善単位は、自然に提示された機材導入依頼の見積、仕入れ、設定・復元、納入、入金まで。

- 資料、実際の型式の機器、受入条件が、違う造形と接続で見える。
- 図から対象・照合条件を確認し、機器から仕入れへ進める。見るだけでは測定、保存状態、現金、原本を変更しない。
- 金額変更が相場、基本料の予算上限、利益、顧客評価への価格効果へ反映される。見積不成立と保存失敗が固定操作の近くに見える。
- 保存した見積、同じ機器番号、実際の復元資料が、中断・再開後の納品と請求まで残る。
- 960×600・文字130%と大画面で主要操作ができる。色に加えて破線、空の印、＋、↓、✓、×、! と状態名を使う。

## 表示と状態の所有

営業の導入設計は紺の方眼面、資料の束、既存の機材画像、復元トレーを使う。実際に操作する準備台、バックアップソフト、診断、納品書とは役割を分ける。破線は導入予定であり、稼働や測定の成功を主張しない。

HardwareQuoteBoard は案件カタログの対象資料と Game.offer_operations_preview の実在庫を読む。会社全体の不足を、案件へ割当済みの機器として表示しない。機器は既存の仕入れ経路を開き、資料と受入印は図内の確認対象だけを変える。

QuotePriceScale は Game.contract_quote の値を使い、相場を円、上限を縦線、提案を三角で示す。顧客予算の判定対象は契約基本料。機材原価は別の請求行として回収され、利益に二重加算しない。経費と利益は同じ見積計算から読む。重複していた見積文章の行は機材案件で隠した。

新しく受ける退避機器の案件には、既存の BackupAuthorization で三資料の原本・対象外の資料・許可された復元先を記録する。/tmp への復元処理が成功しても顧客受入は不合格になる。/restore への復元・内容照合、原本保持、最新の測定、機材受領を分けて納品する。

保存済み VM は保存された旧シナリオと判定数を維持する。現行カタログから原本記録や新しい受入条件を後付けしない。顧客管理の機材導入に残っていた人物の絵も、実際のゲートウェイ・退避機器の画像と業務名へ変えた。

参考は [UniFi の機器トポロジー](https://help.ui.com/hc/en-us/articles/360012192813-Introduction-to-UniFi)と、[Synology の保存・復元の分離](https://www.synology.com/en-global/dsm/feature/active-backup-business/physical-server)。外部サービスを使わず、ゲーム既存の描画と状態で構成した。

## 操作による検証

証拠はリポジトリ外の ../audit/intake-impact-20261006/ に保存。

test_hardware_quote_native.gd は、前回本当に納品・入金まで操作した DAY 06 の continuation-completed.json を QA にコピーする。今回の資金、スキル、提示案件、設定、実ファイル、成功判定を代入しない。受注以降は Godot のマウス・キーイベントを使う。入荷30秒・発送12秒は実際の配送タイマーを動かす。背景の業務時計を止めても明示的な作業時間と経費は残す。

通常オフィスと同じ Graphics.apply_settings を適用する。物理ウィンドウだけ960にした検証とは区別し、狭い画面の論理座標も960×600、文字設定も1.3で確認する。

失敗と再開の操作は、基本料0の赤字、実予算より1円高い見積の不成立、価格修正と下書き保存、UIを破棄して保存後再開、QA保存先の故意の失敗と再試行、未検証機材の発送拒否、/tmp への復元と /restore への修正、復元後・納入前の保存再開。

最後に同じ WHB-2 の機器番号と合意基本料で納品し、実請求を入金済みにする。顧客満足と現金の変化は completed.json と請求台帳に残す。

最終版の退避機器の入力検証は、狭い画面・大画面とも359確認、57クリック、59キーで不合格0。狭い画面9回、大画面11回のスクロールを含む。両方とも DAY 06 の自然な提示案件から、基本料 ¥8,500、材料 ¥4,800、同じ機器番号 WHB-000002 で納品した。期限内評価、顧客満足70→75、請求 INV/0007 の入金を実データで確認した。配布版の第三者プレイではなく、既存セーブを使った開発者の入力検証である。

初期の不合格ログも保持する。最初の通しで従来の機材案件に受入記録がないことを確認し、新規案件に原本記録を追加した。価格図の検証では、中心だけを見る・画面上端へ戻すという不適切なテストのスクロール条件を修正し、図全体と各ラベルのクリッピングを確認するようにした。ファイル名を含む診断ノードの識別子も Godot の正規化後の名前に合わせた。これらを最終版の成功として扱わない。

準備台の既存ゲートウェイ入力テストにも、通常オフィスと同じ表示設定を適用した。これにより960×600・130%で、選択機器の下端が固定操作欄の裏に入る問題を検出した。機器選択、接続・発送操作、保存後再開で、レイアウト後に選択機器全体を表示するよう修正した。背景更新で勝手にスクロールせず、機器の位置・設定・フォーカスを変更しない。

この準備台の可視性修正後は、既存のゲートウェイの受注から請求入金までの実入力テストを960×600・130%で通した。293確認、43クリック、25キー、12回のスクロール、不合格0。最初の通常案件の資金準備は公開APIで行い、その後の機材案件は実入力で進めた。退避機器の359確認は、この追加の準備台スクロール修正前の記録である。

関連チェックは市場UI、経済、退避機器の受入と旧機材VM互換、原本保全91確認、顧客管理UI140確認で不合格0。実際の古いプレイヤーセーブは33確認で再開し、保存元の SHA-256 は 9ceabc887485dc835df3dec6e89b75c96a600025b54b4090d5b422e062c110f8 のまま。旧機材VMは明示的なモデル互換用の合成データであり、実プレイヤーセーブと分けて扱う。最初の旧セーブ実行は外部スクリプトの相対パスが解決できず失敗したため、絶対パスで実行し直した。

## 限界と次の優先課題

開発者による通常GUIの目視・操作と、自動入力によるプレイ検証である。初見の第三者プレイヤーは未検証であり、「面白い」「直感的」とは判定していない。

今回の導入設計図は機材案件に限定している。通常の運用・トラブル依頼の受注一覧はまだ名称と価格が中心。次は通常依頼を一件進めて、利用者・対象・困っている業務・残すべき経路が受注時に見えない問題を優先する。同じ図を全案件へ貼る前に、違う仕事の対象と判断を確認する。
